# agx — Agent Environment Manager

## Design Specification v0.1.0 (Draft)

---

## 1. Overview

`agx` is a package manager for agent environments. It creates isolated, reproducible configurations for AI coding agents by managing plugins, skills, subagents, MCP servers, and related assets — the same way Cargo manages Rust crates or uv manages Python packages.

The tool is **backend-agnostic**. While the primary target is Claude Code, `agx` supports multiple agent frameworks (Gemini CLI, Codex, Cursor, etc.) through a pluggable backend system. A single manifest can generate correct configurations for multiple backends simultaneously.

### Core Principles

- **Reproducibility.** Two developers cloning the same repo and running `agx install` get identical agent environments, regardless of what's installed on their machines globally.
- **Isolation.** By default, only project-declared assets are available. User-level and global configurations are suppressed to prevent "it works on my machine" drift.
- **Familiarity.** The workflow mirrors established package managers: a human-authored manifest, an auto-generated lockfile, a global cache, and generated output that is never committed to version control.

### Design Influences

| Concept | Cargo (Rust) | uv (Python) | agx |
|---|---|---|---|
| Manifest | `Cargo.toml` | `pyproject.toml` | `agent-environment.yml` |
| Lockfile | `Cargo.lock` | `uv.lock` | `agent-environment.lock` |
| Cache | `~/.cargo/` | `$XDG_CACHE_HOME/uv` | `$XDG_CACHE_HOME/agx` |
| Local output | `target/` | `.venv/` | `.agx/` + generated backend dirs |
| Registry | crates.io | PyPI | Federated git-based marketplaces |

## 2. File Layout

### 2.1 Committed Files (version controlled)

```
my-project/
├── agent-environment.yml          # The manifest (human-edited)
├── agent-environment.lock         # Pinned dependency resolution (auto-generated)
├── CONTEXT.md                     # Shared project context (base for all backends)
├── CONTEXT.claude-code.md         # Claude Code-specific overlay
├── CONTEXT.gemini-cli.md          # Gemini CLI-specific overlay
├── agents/                        # User-authored local assets (conventional default)
│   └── my-reviewer.md
└── skills/
    └── deploy-checklist/
        └── SKILL.md
```

Only the manifest, the lockfile, context source files, and any user-authored local assets are committed to git. Everything else is reproducible from these files.

### 2.2 Project-Local Generated Files (gitignored)

```
my-project/
├── .agx/                          # agx workspace (gitignored)
│   ├── integrity.json             # maps lockfile entries → cache paths + checksums
│   └── state.json                 # last-generate metadata for change detection
├── CLAUDE.md                      # ← generated by agx (merged CONTEXT.md + CONTEXT.claude-code.md)
├── .claude/                       # generated by agx for claude-code backend
│   ├── settings.json
│   ├── agents/
│   │   ├── my-reviewer.md         # copied from local agents/
│   │   └── code-reviewer.md       # copied from global cache (plugin asset)
│   └── skills/
│       └── deploy-checklist/
├── .mcp.json                      # generated by agx for claude-code backend
├── GEMINI.md                      # ← generated by agx (merged CONTEXT.md + CONTEXT.gemini-cli.md)
├── .gemini/                       # generated by agx for gemini-cli backend
│   └── skills/
└── AGENTS.md                      # ← generated by agx (base CONTEXT.md only, for generic tools)
```

`agx` generates these directories from the resolved lockfile and global cache. They are disposable and should be gitignored. A suggested `.gitignore` is created by `agx init`.

### 2.3 Global Cache (user-level, shared across projects)

```
$XDG_CACHE_HOME/agx/              # ~/.cache/agx on Linux
│                                  # ~/Library/Caches/agx on macOS
│                                  # %LOCALAPPDATA%\agx\cache on Windows
├── plugins/                       # downloaded plugin archives, keyed by source + version
│   └── anthropics-claude-plugins-official/
│       └── quality-review@1.2.0/
├── skills/                        # individual skills, keyed by repo + ref
│   └── vercel-labs-agent-skills@abc123def/
│       └── web-design-guidelines/
├── git/                           # bare git repo clones (like Cargo's git/db)
│   └── github.com-anthropics-claude-plugins-official.git
├── registry/                      # cached marketplace index metadata
│   └── anthropics-claude-plugins-official/
│       └── marketplace.json
└── tmp/                           # transient download staging
```

The global cache is safe to delete at any time; `agx install` will repopulate it. It is shared across all projects, so if two projects depend on the same plugin version, the download happens once.

**Environment variable override:** `AGX_CACHE_DIR`

**Inspection:** `agx cache dir` prints the current cache path.

**Cleanup:** `agx cache clean` removes all cached data. `agx cache clean <name>` removes entries for a specific asset.

## 3. Manifest Format (`agent-environment.yml`)

The manifest is the single source of truth for the agent environment. It is human-authored, YAML-formatted, and committed to version control.

### 3.1 Full Example

```yaml
# agent-environment.yml
name: my-agent-project
version: 0.1.0
description: An agent environment for the Acme backend service

# --- Backend Configuration ---

backends:
  claude-code:
    default: true
    isolation: strict                # strict | permissive (default: strict)
    model:
      id: sonnet                     # default model for the session
      effort: high                   # low | medium | high
      plan_model: opus               # use Opus for plan mode, Sonnet for execution
      available:                     # models that can be switched to mid-session
        - sonnet
        - opus
        - haiku
  gemini-cli:
    isolation: permissive
    model:
      id: gemini-2.5-pro
      parameters:                    # Gemini-specific hyperparameters
        temperature: 0.7
        thinking_budget: 4096

# --- Registries ---
# Named references to plugin marketplaces (git-based catalogs).

registries:
  official:
    url: https://github.com/anthropics/claude-plugins-official
  community:
    url: https://github.com/kivilaid/plugin-marketplace
  internal:
    url: https://github.com/acme-corp/private-plugins
    auth: token                      # signals that AGX_REGISTRY_INTERNAL_TOKEN is needed

# --- Plugins ---
# Installable bundles from marketplace registries.
# Each plugin may contain agents, skills, commands, hooks, and MCP configs.

plugins:
  quality-review:
    registry: official
    version: ">=1.0.0, <2.0.0"      # semver range
  supabase-toolkit:
    registry: community
    version: "~1.3.0"               # compatible with 1.3.x
  internal-tools:
    registry: internal
    version: "2.1.0"                 # exact pin
  # Plugins can also come from direct git references
  custom-plugin:
    git: https://github.com/someone/their-plugin.git
    tag: v3.0.0                      # or: branch, commit

# --- Skills ---
# Individual skills, either from registries like skills.sh, git repos, or local paths.

skills:
  web-design-guidelines:
    git: https://github.com/vercel-labs/agent-skills
    path: skills/web-design-guidelines   # path within the repo
    tag: v2.1.0
  react-best-practices:
    git: https://github.com/vercel-labs/agent-skills
    path: skills/react-best-practices
    commit: abc123def456             # exact commit pin
  deploy-checklist:
    path: ./skills/deploy-checklist  # local, user-authored

# --- Agents ---
# Subagent definitions. Can reference marketplace plugins, git repos, or local files.

agents:
  my-reviewer:
    path: ./agents/my-reviewer.md    # local, user-authored
    model: opus                      # uses Opus regardless of project default
  security-scanner:
    git: https://github.com/wshobson/agents
    path: plugins/security-review/agents/security-auditor.md
    branch: main
    model: opus                      # security work benefits from stronger reasoning
    parameters:
      temperature: 0.1               # conservative for security analysis
      thinking_budget: 8192          # deep reasoning (Gemini CLI)
  quick-linter:
    path: ./agents/quick-linter.md
    model: haiku                     # lightweight, fast, cheap
    parameters:
      temperature: 0.0               # fully deterministic

# --- MCP Servers ---
# Runtime service integrations. These are not downloaded — they are configured.

mcp-servers:
  playwright:
    url: https://mcp.playwright.dev/sse
  filesystem:
    command: npx
    args:
      - "@anthropic-ai/mcp-server-filesystem"
      - "./src"
    env:
      ALLOW_WRITE: "true"
  postgres:
    command: npx
    args:
      - "@anthropic-ai/mcp-server-postgres"
    env:
      DATABASE_URL: "${DATABASE_URL}"  # resolved from environment at generate time

# --- Settings ---
# Backend-specific settings that get merged into generated config files.
# Use this instead of manually editing generated files.

settings:
  claude-code:
    permissions:
      allow:
        - "Bash(npm test)"
        - "Bash(npm run lint)"
      deny:
        - "Bash(rm -rf)"
    environment:
      CLAUDE_CODE_DISABLE_BACKGROUND_TASKS: "1"
  gemini-cli:
    safety_settings:
      harassment: block_none

# --- Local Asset Paths ---
# Override conventional defaults for where user-authored assets live.
# Defaults: agents/ and skills/ at the project root.

paths:
  agents: ./custom/agents            # default: ./agents
  skills: ./custom/skills            # default: ./skills

# --- Context Files ---
# Project instructions loaded by backends at session start (CLAUDE.md, GEMINI.md, etc.).
# Write a shared base and optional per-backend overlays. agx merges and places them.

context:
  base: ./CONTEXT.md                 # shared project context (committed)
  overlays:                          # backend-specific additions (committed)
    claude-code: ./CONTEXT.claude-code.md
    gemini-cli: ./CONTEXT.gemini-cli.md
  children:                          # subdirectory context files (monorepo support)
    - path: ./packages/api
      base: ./packages/api/CONTEXT.md
      overlays:
        claude-code: ./packages/api/CONTEXT.claude-code.md
    - path: ./packages/web
      base: ./packages/web/CONTEXT.md
```

### 3.2 Section Reference

#### `name`, `version`, `description`

Project metadata. `name` is required. `version` follows semver. These are informational and used in lockfile metadata.

#### `backends`

Declares which agent frameworks this project targets. At least one backend is required.

| Field | Type | Default | Description |
|---|---|---|---|
| `default` | `bool` | `false` | If true, this backend is launched by `agx run` when no backend is specified. If omitted, the first listed backend is the default. |
| `isolation` | `strict \| permissive` | `strict` | In `strict` mode, user-level and global assets are disabled. In `permissive`, project assets layer on top of existing user config. |
| `model` | `string \| object` | (backend default) | Default model for the session and agents. See Model Configuration below. |

**Model Configuration**

The `model` field accepts either a simple string (alias or full model ID) or an object for more control:

```yaml
# Simple — alias or full model ID
model: sonnet

# Full model ID with version pin
model: claude-opus-4-6

# Extended context
model: opus[1m]

# Object form — additional options
model:
  id: claude-opus-4-6           # alias or full model ID
  extended_context: true         # equivalent to [1m] suffix (backend-specific)
  effort: high                   # low | medium | high (backend-specific)
  plan_model: opus               # model used in plan mode (Claude Code's opusplan concept)
  available:                     # restrict which models can be switched to mid-session
    - sonnet
    - opus
    - haiku
  parameters:                    # backend-specific hyperparameters (passed through as-is)
    temperature: 0.7
    top_p: 0.95
    max_output_tokens: 8192
    thinking_budget: 4096
```

**The `parameters` map.** This is a generic key-value passthrough for backend-specific hyperparameters. `agx` does not validate or interpret these values — they are written directly into the generated backend configuration. This allows teams to pin generation parameters for reproducibility without `agx` needing to model every backend's parameter set.

Common parameters by backend:

| Backend | Example parameters |
|---|---|
| `claude-code` | `effort` (via the dedicated field above) |
| `gemini-cli` | `temperature`, `top_p`, `max_output_tokens`, `thinking_budget`, `include_thoughts` |
| `codex` | `temperature`, `max_tokens`, `reasoning_effort` |

For Gemini CLI specifically, `agx generate` maps the `parameters` into the `modelConfigs` system — either as a custom alias or as properties in `settings.json`, depending on the parameter. For Claude Code, applicable parameters are translated into settings or environment variables as appropriate.

Model identifiers are backend-specific. `agx` passes them through to the generated configuration without validation, since model availability depends on the user's subscription tier and provider. Examples:

| Backend | Example model values |
|---|---|
| `claude-code` | `sonnet`, `opus`, `opus[1m]`, `opusplan`, `claude-opus-4-6`, `claude-sonnet-4-6`, `claude-haiku-4-5-20251001` |
| `gemini-cli` | `gemini-2.5-pro`, `gemini-2.5-flash`, `gemini-3-pro-preview` |
| `codex` | `o3`, `o4-mini`, `codex-mini` |

**Per-agent model and parameter overrides.** Individual agents can specify their own model and parameters in the manifest, overriding the backend defaults. This is useful when a specialized agent needs a more capable (or cheaper) model, or different generation behavior, than the project baseline:

```yaml
agents:
  my-reviewer:
    path: ./agents/my-reviewer.md
    model: opus                      # this agent uses Opus regardless of project default
  security-scanner:
    path: ./agents/security-scanner.md
    model: opus
    parameters:                      # conservative settings for security analysis
      temperature: 0.1
      thinking_budget: 8192
  quick-linter:
    path: ./agents/quick-linter.md
    model: haiku                     # lightweight agent uses Haiku for speed/cost
    parameters:
      temperature: 0.0               # fully deterministic
```

When `agx generate` writes the agent Markdown file for Claude Code, it sets the `model` field in the agent's YAML frontmatter. For backends that don't support per-agent models, the override is ignored with a warning.

#### `registries`

Named references to federated plugin marketplaces. Each registry points to a git repository containing a `.claude-plugin/marketplace.json` (or equivalent for other backends). Registries are fetched and cached at the global level.

The `auth` field signals that an environment variable is required for private registries, following the convention `AGX_REGISTRY_{UPPER_SNAKE_NAME}_TOKEN`.

#### `plugins`

Dependencies on plugin bundles from registries or direct git sources.

**From a registry:**

| Field | Type | Required | Description |
|---|---|---|---|
| `registry` | `string` | yes | Name of a registry defined in `registries` |
| `version` | `string` | yes | Semver version constraint |

**From git:**

| Field | Type | Required | Description |
|---|---|---|---|
| `git` | `string` | yes | Git repository URL |
| `tag` | `string` | one of tag/branch/commit | Git tag |
| `branch` | `string` | | Git branch |
| `commit` | `string` | | Full commit SHA |

#### `skills`

Individual skills from git repositories or local paths.

| Field | Type | Required | Description |
|---|---|---|---|
| `git` | `string` | if remote | Git repository URL |
| `path` | `string` | yes | Path within repo (for git) or local path (starts with `./`) |
| `tag` | `string` | optional | Git tag |
| `branch` | `string` | optional | Git branch |
| `commit` | `string` | optional | Full commit SHA |

When no tag/branch/commit is specified for a git source, `agx lock` resolves to the latest commit on the default branch and pins it in the lockfile.

#### `agents`

Individual subagent definitions. Same source fields as `skills`, plus an optional `model` override.

| Field | Type | Required | Description |
|---|---|---|---|
| `git` | `string` | if remote | Git repository URL |
| `path` | `string` | yes | Path within repo (for git) or local path (starts with `./`) |
| `tag` | `string` | optional | Git tag |
| `branch` | `string` | optional | Git branch |
| `commit` | `string` | optional | Full commit SHA |
| `model` | `string` | optional | Model override for this agent. Overrides the backend-level default. Uses the same identifier format (alias or full model ID). |
| `parameters` | `map[string, any]` | optional | Backend-specific hyperparameters for this agent (e.g., `temperature`, `thinking_budget`). Passed through to the generated config without validation. |

When a `model` or `parameters` are specified on an agent, `agx generate` injects or overrides the corresponding fields in the agent's configuration for each backend. For Claude Code, this means setting the `model` field in YAML frontmatter. For Gemini CLI, this means setting `model`, `temperature`, and other frontmatter fields, as well as generating `modelConfigs.overrides` entries scoped to that agent. For backends that don't support a given field, a warning is emitted and the field is ignored.

#### `mcp-servers`

Runtime service integrations. Two forms:

**Remote (URL-based):**

| Field | Type | Required | Description |
|---|---|---|---|
| `url` | `string` | yes | SSE endpoint URL |

**Local (command-based):**

| Field | Type | Required | Description |
|---|---|---|---|
| `command` | `string` | yes | Executable command |
| `args` | `list[string]` | optional | Command arguments |
| `env` | `map[string, string]` | optional | Environment variables. Values starting with `${}` are resolved from the shell environment. |

MCP servers are not downloaded or cached. The `agx generate` step writes their configuration into the appropriate backend config files (e.g., `.mcp.json` for Claude Code).

#### `settings`

Per-backend key-value settings that are merged into generated configuration files. This is the escape hatch for backend-specific options that `agx` doesn't model as first-class fields.

Anything placed here is written directly into the backend's config file during `agx generate`. This replaces the need to manually edit generated files.

#### `paths`

Override the conventional default locations for local assets.

| Field | Default | Description |
|---|---|---|
| `agents` | `./agents` | Directory containing local agent Markdown files |
| `skills` | `./skills` | Directory containing local skill directories |

#### `context`

Manages project instruction files (`CLAUDE.md`, `GEMINI.md`, `AGENTS.md`, etc.) using a shared base with optional per-backend overlays. This avoids duplicating 80%+ of identical content across backend-specific files.

**How it works.** During `agx generate`, for each declared backend:

1. The `base` file is read as the foundation.
2. If an `overlay` exists for that backend, its content is appended after the base (separated by a generated marker comment).
3. The merged result is written to the backend's expected location and filename.

For example, with `claude-code` as a backend, `agx generate` merges `CONTEXT.md` + `CONTEXT.claude-code.md` and writes the result to `CLAUDE.md` at the project root. For `gemini-cli`, it merges `CONTEXT.md` + `CONTEXT.gemini-cli.md` and writes `GEMINI.md`.

| Field | Type | Required | Description |
|---|---|---|---|
| `base` | `string` | yes | Path to the shared context Markdown file. Contains backend-agnostic project instructions (structure, commands, conventions). |
| `overlays` | `map[string, string]` | optional | Per-backend overlay files. Keys are backend names, values are file paths. Content is appended to the base during generation. |
| `children` | `list[object]` | optional | Subdirectory context files for monorepo support. Each entry specifies a `path`, `base`, and optional `overlays`. |

**Overlay content guidelines.** The base file should contain everything that applies to all backends: project description, directory structure, build/test commands, coding conventions, architecture notes. Overlays should contain only backend-specific instructions, such as:

- Claude Code overlay: references to `/compact`, MCP server usage tips, Claude-specific memory instructions
- Gemini CLI overlay: references to `/model`, extension usage, sandbox configuration

**Subdirectory context (monorepo support).** The `children` list allows declaring context files for subdirectories. When `agx generate` runs, each child's merged context file is written to the appropriate location within its subdirectory:

```
packages/api/CLAUDE.md        ← merged from packages/api/CONTEXT.md + packages/api/CONTEXT.claude-code.md
packages/api/GEMINI.md        ← merged from packages/api/CONTEXT.md (no Gemini overlay declared)
packages/web/CLAUDE.md        ← merged from packages/web/CONTEXT.md
```

If no overlay exists for a given backend, the base is used as-is.

**Generated file markers.** Merged context files include a comment at the top indicating they were generated:

```markdown
<!-- AUTO-GENERATED BY agx from CONTEXT.md + CONTEXT.claude-code.md. DO NOT EDIT. -->
<!-- To modify, edit the source files and run: agx generate -->

[merged content here]
```

**Null context.** If the `context` section is omitted from the manifest entirely, `agx` does not generate or manage any context files. Existing `CLAUDE.md` or `GEMINI.md` files in the project are left untouched. This allows gradual adoption — teams can start managing other assets with `agx` and adopt context management later.

**What about `AGENTS.md`?** The emerging `AGENTS.md` standard is a backend-agnostic context file recognized by multiple tools (Cursor, Codex, Windsurf, etc.). When generating for backends that recognize `AGENTS.md`, `agx` writes just the base file (no overlay needed since `AGENTS.md` is inherently generic). This means a single `CONTEXT.md` can serve as the source for both `AGENTS.md` (generic) and `CLAUDE.md` / `GEMINI.md` (with overlays).

## 4. Lockfile (`agent-environment.lock`)

The lockfile is auto-generated by `agx lock` or `agx install`. It pins every dependency to an exact, reproducible reference. It is committed to version control.

### 4.1 Purpose

The lockfile ensures that `agx install` produces identical results on any machine at any time. It records:

- The exact resolved version (or commit SHA) of every plugin, skill, and agent.
- The integrity hash (SHA-256) of each downloaded asset.
- The registry or git source from which each asset was resolved.

### 4.2 Format

The lockfile is YAML for consistency with the manifest.

```yaml
# agent-environment.lock
# AUTO-GENERATED BY agx. DO NOT EDIT.
lockfile_version: 1
generated_at: "2026-03-19T10:30:00Z"
agx_version: "0.1.0"

plugins:
  quality-review:
    source:
      registry: official
      resolved_version: "1.2.0"
    git_commit: "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2"
    integrity: "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"

  supabase-toolkit:
    source:
      registry: community
      resolved_version: "1.3.2"
    git_commit: "b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3"
    integrity: "sha256:d7a8fbb307d7809469ca9abcb0082e4f8d5651e46d3cdb762d02d0bf37c9e592"

  internal-tools:
    source:
      registry: internal
      resolved_version: "2.1.0"
    git_commit: "c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4"
    integrity: "sha256:ef2d127de37b942baad06145e54b0c619a1f22327b2ebbcfbec78f5564afe39d"

skills:
  web-design-guidelines:
    source:
      git: https://github.com/vercel-labs/agent-skills
      path: skills/web-design-guidelines
    git_commit: "d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5"
    integrity: "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"

  react-best-practices:
    source:
      git: https://github.com/vercel-labs/agent-skills
      path: skills/react-best-practices
    git_commit: "abc123def456abc123def456abc123def456abc123"
    integrity: "sha256:4e07408562bedb8b60ce05c1decfe3ad16b72230967de01f640b7e4729b49fce"

  deploy-checklist:
    source:
      local: ./skills/deploy-checklist
    # No git_commit or integrity for local assets

agents:
  my-reviewer:
    source:
      local: ./agents/my-reviewer.md

  security-scanner:
    source:
      git: https://github.com/wshobson/agents
      path: plugins/security-review/agents/security-auditor.md
    git_commit: "e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6"
    integrity: "sha256:ca978112ca1bbdcafac231b39a23dc4da786eff8147c4e72b9807785afee48bb"
```

### 4.3 Lockfile Behavior

- `agx install` reads the lockfile and installs exactly what it says. If no lockfile exists, it resolves from the manifest first (equivalent to `agx lock` + `agx install`).
- `agx update` re-resolves all dependencies within the constraints of the manifest and writes a new lockfile.
- `agx update <name>` re-resolves a single dependency.
- `agx lock` resolves and writes the lockfile without downloading or generating.
- Local assets (`path: ./...`) are always read from disk at generate time and are not pinned in the lockfile.

## 5. Backends

### 5.1 Architecture

Each backend is a module that knows how to render a resolved dependency graph into the file layout and configuration format expected by a specific agent framework. `agx` ships with built-in backends and supports third-party backend plugins in the future.

```
┌─────────────────────────┐
│  agent-environment.yml  │  (manifest)
└────────────┬────────────┘
             │ resolve
             ▼
┌─────────────────────────┐
│  agent-environment.lock │  (pinned versions)
└────────────┬────────────┘
             │ generate
             ▼
     ┌───────┴───────┐
     │               │
     ▼               ▼
┌─────────┐   ┌───────────┐
│ claude-  │   │ gemini-   │   ... (other backends)
│ code     │   │ cli       │
│ backend  │   │ backend   │
└────┬─────┘   └─────┬─────┘
     │               │
     ▼               ▼
  .claude/        .gemini/
  .mcp.json       config
```

### 5.2 Built-in Backends

#### `claude-code`

Generates:
- `CLAUDE.md` — merged from `CONTEXT.md` + `CONTEXT.claude-code.md` (if context section is declared)
- `.claude/settings.json` — project-scoped settings including isolation flags, permissions, model preferences
- `.claude/agents/*.md` — subagent Markdown files with YAML frontmatter
- `.claude/skills/*/SKILL.md` — skill directories
- `.mcp.json` — MCP server configuration at the project root

In `strict` isolation mode, the generated settings disable loading of user-level (`~/.claude/`) and enterprise-level assets.

#### `gemini-cli`

Generates:
- `GEMINI.md` — merged from `CONTEXT.md` + `CONTEXT.gemini-cli.md` (if context section is declared)
- `.gemini/agents/*.md` — subagent Markdown files
- `.gemini/skills/` — skill SKILL.md files
- `.gemini/settings.json` (or equivalent Gemini config)

#### Generic backends (Codex, Cursor, Windsurf, etc.)

For backends that recognize the `AGENTS.md` standard, `agx` generates `AGENTS.md` from the base `CONTEXT.md` alone (no overlay), since the file is inherently backend-agnostic.

The backend interface is designed to be extensible for future frameworks.

### 5.3 Asset Compatibility

Not all assets are portable across backends. Skills using the SKILL.md format with standard frontmatter are broadly compatible. Agents with backend-specific fields (e.g., Claude Code's `tools: Read, Grep, Bash`) are not.

During `agx generate`, each backend:

1. Copies compatible assets from the global cache into its output directory.
2. Skips incompatible assets with a warning (e.g., "agent 'security-scanner' uses Claude Code-specific tool restrictions; skipping for gemini-cli backend").
3. Transforms assets where possible (e.g., mapping Claude Code tool names to Gemini CLI equivalents if a mapping exists).

### 5.4 Isolation Modes

**`strict` (default)**

The generated configuration instructs the backend to use *only* project-scoped assets. For Claude Code, this means generating a `settings.json` that disables user-level and global agent/skill loading. This guarantees reproducibility: the environment is fully defined by the manifest and lockfile.

**`permissive`**

Project assets are installed alongside whatever the user has configured globally. This is useful for personal projects where you want a baseline plus your own customizations. It sacrifices reproducibility for convenience.

## 6. Dependency Resolution

### 6.1 Version Constraints

`agx` supports semver-style version constraints for assets from registries:

| Syntax | Meaning |
|---|---|
| `"1.2.0"` | Exactly 1.2.0 |
| `">=1.0.0, <2.0.0"` | Range (explicit) |
| `"~1.3.0"` | Compatible with 1.3.x (>=1.3.0, <1.4.0) |
| `"^1.3.0"` | Compatible with 1.x.x (>=1.3.0, <2.0.0) |

For git sources without semver, pinning is done via `tag`, `branch`, or `commit`. If only `branch` is specified, `agx lock` resolves it to the current HEAD commit and pins the SHA in the lockfile.

### 6.2 Conflict Resolution

If two plugins provide an asset with the same name (e.g., both provide an agent called `code-reviewer`), `agx` will:

1. **Error by default.** The user must resolve the conflict explicitly.
2. **Support namespacing in the manifest** to disambiguate:

```yaml
plugins:
  plugin-a:
    registry: official
    version: "^1.0.0"
    include:
      agents:
        - code-reviewer           # only include this agent from plugin-a
  plugin-b:
    registry: community
    version: "^2.0.0"
    exclude:
      agents:
        - code-reviewer           # exclude the conflicting agent
```

The `include`/`exclude` fields allow fine-grained control over which assets from a plugin are installed, addressing the earlier question about installing individual assets from large plugins.

#### Existing project (detected agent configuration)

When `agx init` is run in a project that already has agent configuration files, it performs an **environment scan** and scaffolds the manifest from what it finds. This is the primary adoption path for existing projects.

```
$ agx init

Detected:
  Backends:
    ● claude-code
      ├── CLAUDE.md (246 lines)
      ├── .claude/settings.json

    ├── quality-review@1.2.0 (source: anthropics/claude-plugins-official)
    └── supabase-toolkit@1.3.2 (source: kivilaid/plugin-marketplace)

  Skills (.claude/skills/):
    ├── deploy-checklist/ (local, no marketplace match)
    └── web-design-guidelines/ (matched: vercel-labs/agent-skills)

  Agents (.claude/agents/):
    ├── code-reviewer.md (from plugin: quality-review)
    └── security-auditor.md (local, no marketplace match)

? Import detected configuration into agent-environment.yml? yes

  → agx will extract backend-agnostic content into CONTEXT.md

? Mark local assets (deploy-checklist, security-auditor) as local paths? yes

Created: agent-environment.yml (from detected configuration)
Created: agent-environment.lock (pinned to current resolved versions)
Created: CONTEXT.md (extracted from CLAUDE.md — review and refine)

Created: CONTEXT.gemini-cli.md (Gemini-specific content from GEMINI.md)

   - Plugin versions were pinned to currently installed versions
   - MCP servers were imported as-is (check env var references)

   - Context files were split heuristically — verify the base vs. overlay separation

  agx check       Validate the generated manifest
  agx generate    Regenerate configs from the new manifest (replaces existing files)
  agx run         Launch in the managed environment
```

**What the scan detects.** `agx init` inspects the project for configuration files from all known backends:

| Source | What it extracts |
|---|---|
| `.claude/settings.json` | Model preferences, permissions, tool restrictions |
| `.claude/agents/*.md` | Agent definitions — matched against known plugin sources if possible |
| `.claude/skills/*/SKILL.md` | Skill definitions — matched against registries and skills.sh |
| `.mcp.json` | MCP server declarations (URLs, commands, args, env vars) |
| `.claude-plugin/` | Installed plugin metadata and marketplace source |
| `CLAUDE.md` | Project context (becomes `CONTEXT.md` base + overlay) |
| `.gemini/settings.json` | Gemini CLI configuration |
| `.gemini/agents/*.md` | Gemini agent definitions |
| `GEMINI.md` | Project context (merged into overlay or diffed against base) |
| `AGENTS.md` | Generic context (candidate for `CONTEXT.md` base) |

**Plugin source matching.** For each detected skill and agent, `agx` attempts to match it against known marketplace registries by comparing file content, names, and metadata. If a match is found, the asset is declared as a registry dependency with a pinned version. If no match is found, it's declared as a local path.

**Context file splitting.** When converting an existing `CLAUDE.md` into `CONTEXT.md` + `CONTEXT.claude-code.md`, `agx` uses heuristics to separate backend-agnostic content (project structure, commands, conventions) from backend-specific content (Claude-specific commands, MCP references, memory instructions). This split is approximate — the user should review and refine the result. If a `GEMINI.md` also exists, `agx` diffs it against the base to extract Gemini-specific content.

**Non-destructive by default.** `agx init` does not delete or overwrite existing configuration files during the scan phase. The original `.claude/`, `.mcp.json`, `CLAUDE.md`, etc. remain intact until the user explicitly runs `agx generate`, at which point the managed versions replace them. This gives users a chance to review the generated manifest before committing to it.

**Force flag.** `agx init --force` skips the detection step and creates a blank manifest, even if existing configuration is detected. `agx init --scan-only` performs the scan and prints what it found without creating any files.

### 7.7 `agx run`

`agx run` launches a backend agent framework inside the managed environment. It is the recommended way to start a session, as it guarantees the environment is up-to-date and isolation is enforced.

```bash
# Launch the default backend (first listed in the manifest)
agx run

# Launch a specific backend
agx run claude-code
agx run gemini-cli

# Pass arguments through to the underlying tool
agx run claude-code -- --model opus --verbose

# One-shot prompt mode (if the backend supports it)
agx run claude-code -- --print "explain the auth module"
```

**Pre-flight sequence.** Before launching the backend, `agx run` performs these steps:

1. **Manifest check.** Verifies `agent-environment.yml` exists in the current or ancestor directory.
2. **Staleness detection.** If the manifest is newer than the lockfile, or the lockfile is newer than the last generate, `agx run` automatically re-runs the equivalent of `agx install` to bring everything up to date.
3. **Integrity verification.** Confirms that generated backend files match the lockfile. If files have been tampered with or deleted, they are regenerated from cache.
4. **Missing dependencies.** If any cached assets are missing (e.g., cache was cleaned), they are re-downloaded.
5. **Launch.** The backend binary is invoked with isolation-enforcing flags and any user-supplied arguments forwarded.

**Backend launch commands.** Each backend module defines how it translates `agx run` into a concrete process invocation:

| Backend | Underlying command (example) |
|---|---|
| `claude-code` | `claude --project-dir . --no-user-settings --model claude-opus-4-6` |
| `gemini-cli` | `gemini --config .gemini/settings.json --model gemini-2.5-pro` |
| `codex` | `codex --skills-dir .codex/skills/ --model o3` |

The exact flags will vary as these tools evolve. The backend module abstracts this so users don't need to track flag changes across tool versions.

**Default backend.** When `agx run` is called without specifying a backend, it launches the first backend listed in the `backends` section of the manifest. If multiple backends are declared and no default is obvious, `agx run` prompts the user to choose (or the user can set a `default` field):

```yaml
backends:
  claude-code:
    default: true
    isolation: strict
  gemini-cli:
    isolation: permissive
```

**Exit code forwarding.** `agx run` forwards the exit code of the underlying backend process, so it integrates cleanly into scripts and CI pipelines.

**Runtime model override.** The `--model` flag overrides the manifest's model configuration for a single session, without modifying any files:

```bash
# Use Opus for this session even though the manifest defaults to Sonnet
agx run claude-code --model opus

# Use extended context
agx run claude-code --model opus[1m]

# Override both model and effort
agx run claude-code --model opus --effort high
```

This is useful for one-off sessions where you need a different model (e.g., tackling a hard architecture problem with Opus when your team baseline is Sonnet), without changing the committed manifest.

agx init

### 8.2 Adopting agx in an Existing Project

This is the most common onboarding path. A project already has `CLAUDE.md`, `.mcp.json`, installed plugins, custom agents, etc., and the team wants to bring it under `agx` management for reproducibility.

```bash
cd my-existing-project

# Step 1: Scan and generate manifest from existing config
agx init
# agx detects existing files, shows what it found, and asks to import

# Step 2: Review the generated manifest
# The manifest, lockfile, and CONTEXT files are created but existing configs
# are NOT yet overwritten — everything still works as before
cat agent-environment.yml       # review detected plugins, skills, agents, MCP servers
cat CONTEXT.md                  # review the base context extracted from CLAUDE.md

# Step 3: Validate
agx check                       # verify manifest is consistent, no conflicts

# Step 4: Switch to managed mode
agx generate                    # overwrites .claude/, .mcp.json, CLAUDE.md with managed versions
agx run                         # launch in the fully managed environment

# Step 5: Commit
git add agent-environment.yml agent-environment.lock CONTEXT.md CONTEXT.claude-code.md
git commit -m "chore: adopt agx for agent environment management"
```

After this, teammates can clone the repo and `agx run` to get an identical environment. The original hand-maintained config files are replaced by generated ones, but all the content is preserved in the manifest and context source files.

## 12. Security Considerations

### 12.1 Integrity Verification

Every asset downloaded from a remote source has its SHA-256 hash recorded in the lockfile. On `agx install`, cached assets are verified against these hashes before being placed into the generated output. A mismatch aborts the install with an error.

### 12.2 Private Registries

Private git-based marketplaces are supported through token-based authentication. Tokens are provided via environment variables, never stored in the manifest or lockfile.

### 12.3 MCP Server Environment Variables

MCP server configurations may reference environment variables using `${VAR_NAME}` syntax. These are resolved at `agx generate` time from the current shell environment. The resolved values are written into the generated config files (which are gitignored), ensuring secrets never appear in committed files.

### 12.4 Asset Review

`agx` does not sandbox or verify the content of skills and agents. Users are responsible for reviewing assets before adding them to their manifest, just as developers review npm packages or crate dependencies. The `agx info <asset>` command can display asset metadata and source information to aid in review.

## 13. Future Considerations

The following are out of scope for v0.1 but are anticipated for future versions:

- **`agx publish`** — publish a skill, agent, or plugin to a marketplace registry.
- **Workspace support** — manage multiple related agent environments (analogous to Cargo workspaces or npm workspaces) for monorepo setups.
- **Backend plugins** — allow third-party backends to be installed as agx extensions.
- **Dependency graph visualization** — `agx graph` to output a visual dependency tree.
- **Asset compatibility matrix** — machine-readable metadata on which assets support which backends, enabling smarter cross-backend generation.
- **Hook support** — declare pre/post install/generate hooks in the manifest for custom automation.
- **Integrity pinning for registries** — pin the registry index itself to a commit, so even the catalog is reproducible.
